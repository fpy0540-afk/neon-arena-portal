# Neon Arena Player Portal

Многостраничный статический портал для игроков Neon Arena. Без внешних CDN и без платёжных интеграций.

## Страницы / Pages

- `index.html` — главная / Home
- `account.html` — вход, полноценная регистрация, профиль и восстановление пароля / Sign-in, sign-up, profile and password recovery
- `collection.html` — личная коллекция синхронизированных скинов / Private synced skin collection
- `stats.html` — личная статистика матчей и игровых кредитов / Private match and credit stats
- `sessions.html` — просмотр и отзыв сессий / Review and revoke sessions
- `market.html` — скины за игровые кредиты / Cosmetic skin market using game credits
- `servers.html` — поиск комнат и копирование приглашения / Find rooms and copy invites
- `updates.html` — обновления и полезная информация / Updates and helpful notes
- `help.html` — краткая помощь / Quick help

## Настройка Supabase / Supabase setup

Портал уже заполнен публичными Project URL и publishable key проекта Neon Arena. Такой ключ предназначен для клиентских приложений и находится в `assets/site-config.js`; Godot использует те же значения как значения по умолчанию, но локальные настройки игрока могут их переопределить.

ZIP содержит только статический сайт. Чтобы включить аккаунты, сессии, синхронизированную коллекцию, статистику, рынок и каталог комнат, владелец проекта должен выполнить **весь** `supabase/schema.sql` в Supabase Dashboard → SQL Editor → New query → Run. Схема создаёт таблицы и профиль для уже существующих Auth-пользователей. Если база уже содержит старую версию, проверь и при необходимости примени `supabase/migrations/20261026_web_portal_session_header.sql`. Затем добавь полный URL страницы аккаунта GitHub Pages в Supabase Auth → URL Configuration → Redirect URLs (например, `https://USERNAME.github.io/REPOSITORY/account.html`).

**Код подтверждения регистрации:** страница аккаунта показывает поле для кода и отправляет его в Supabase Auth для проверки. Чтобы Supabase присылал код, а не ссылку, в Dashboard открой Authentication → Email Templates → **Confirm signup** и используй `{{ .Token }}` вместо `{{ .ConfirmationURL }}`. Например: `<h2>Код Neon Arena</h2><p>Введи этот код на странице аккаунта:</p><p style="font-size:24px;font-weight:bold">{{ .Token }}</p>`. Не добавляй в это письмо кликабельную ссылку подтверждения, чтобы почтовый сканер случайно не использовал одноразовый токен. Сброс пароля по-прежнему использует ссылку — шаблон восстановления не меняй.

**Доставка писем:** встроенная тестовая почта Supabase может не отправлять обычным игрокам. Настрой свой SMTP в Dashboard → Authentication → Emails → SMTP Settings, а при сбое смотри Authentication Logs и логи почтового провайдера. SMTP-пароль и secret/service-role ключи никогда не добавляй в сайт или ZIP. См. [Supabase email templates](https://supabase.com/docs/guides/auth/auth-email-templates) и [настройку SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

**Никогда не вставляй сюда `service_role`, `sb_secret_*`, пароль или другие секреты.** В публичном сайте допустим только anon/publishable key, и только вместе с настроенными RLS-политиками из схемы проекта.

## Публикация на GitHub Pages вручную / Manual GitHub Pages publishing

1. Распакуй ZIP на компьютере. В GitHub открой корень репозитория и выбери **Add file → Upload files**.
2. Загрузи **содержимое** распакованной папки, а не саму папку: все девять HTML-страниц, `README.md` и папку `assets`. После загрузки в корне GitHub-репозитория должны сразу быть `index.html` и `assets/` — не только папка `NEON_ARENA_GITHUB_PAGES`.
3. Нажми **Commit changes**. `assets/site-config.js` уже настроен на проект Neon Arena; не заменяй публичный ключ на секретный и не удаляй конфигурацию.
4. На GitHub открой **Settings → Pages**, выбери публикацию из ветки `main`, папку `/(root)`, затем **Save**.
5. После публикации проверь главную страницу и переходы на `/account.html`, `/collection.html`, `/stats.html`, `/sessions.html`, `/market.html`, `/servers.html`, `/updates.html`, `/help.html`.

Если SQL-схема ещё не применена к Supabase, сам сайт откроется, но функции, требующие таблиц, пока не заработают. Публикацию из этой среды выполнить нельзя; ZIP предназначен для ручной загрузки.

## Поведение и ограничения

- Регистрация проверяет email, имя, длину пароля и его повтор; после регистрации открывается поле для кода подтверждения email. Сам код нигде не сохраняется; адрес email хранится только в sessionStorage текущей вкладки, чтобы восстановить форму после перезагрузки. Есть повторная отправка кода и сброс пароля по email.
- До входа страницы сессий, статистики и коллекции скрывают личные данные. Запросы выполняются только после входа и явного нажатия игроком соответствующей кнопки.
- Страницы не выполняют фоновые проверки интернета. Данные загружаются только после нажатия соответствующей кнопки; большие списки постранично загружаются до настроенного лимита (5 000 или 10 000 строк) и показывают предупреждение о неполных итогах при его достижении.
- Идентификаторы приложения и сессии случайные; HWID не собирается. Состояние входа хранится в пределах вкладки; токен recovery временно хранится в sessionStorage, чтобы восстановить форму после reload, затем удаляется при сбросе или отмене. Парольные поля и профиль очищаются после выхода.
- Рынок использует только внутриигровые кредиты, без реальных платежей. Для защиты экономики от читов нужны доверенные игровые серверы/Edge Functions.
- Список комнат зависит от опубликованного игровым хостом heartbeat; адреса Cloudflare Quick Tunnel временные, поэтому приглашение может устареть.
- Поддерживаются английский и русский языки. Цветовой акцент можно менять пресетами или вручную; для основного градиентного действия подбирается контрастный цвет текста. Выбор сохраняется в браузере. Анимации отключаются настройкой системы «уменьшение движения». Внешние CDN не используются.


## Результаты клиентского аудита / Front-end audit notes (2026-10-27)

Исправления сайта закрывают безопасную отправку форм без JavaScript, очистку паролей/профиля, проверку нулевых ответов PATCH, честное предупреждение при неподтверждённом сервером выходе, восстановление recovery-flow и шага ввода кода после reload, OTP-подтверждение регистрации, защиту от повторных кликов, пагинацию с видимым лимитом, состояние загрузки рынка/коллекции, локализацию ошибок схемы, клавиатурные вкладки, заметный fallback копирования приглашения и адаптивность узких экранов. Это именно клиентские меры.

Они **не доказывают** готовность Supabase: ранее live REST вернул `PGRST205` для portal-таблиц. Владелец должен применить `supabase/schema.sql`, настроить шаблон Confirm signup на `{{ .Token }}` и SMTP, затем отдельно проверить RLS/column grants, PostgREST cache, атомарность RPC рынка, отзыв реальных Auth-сессий и серверную уникальность/агрегацию наград. SQL/RLS, реальная доставка email и игровой authoritative server не подтверждаются тестами статического сайта. Визуальный браузерный тест на 320 px также не запускался — выполнены статические и Node-регрессии.

## Tests / Проверки

Из корня **полного архива исходников** выполни `python tests/test_web_portal_static.py`, `node tests/test_web_portal_keys.mjs` и `node tests/test_web_portal_auth.mjs`. Они проверяют разметку/ссылки, EN/RU каталоги, безопасную отправку форм, код подтверждения регистрации, pagination/status, нулевые PATCH-результаты, локальный/серверный выход, recovery и ожидающий OTP после reload, публичный ключ и отсутствие фоновых сетевых запросов. В Pages-only ZIP папки `tests/` намеренно нет — тесты включены в полный ZIP источников.
